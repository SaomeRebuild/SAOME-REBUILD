## ⚠️ Live Capture 揭露的 Contract Drift（4 個 + 1 root cause）

### Drift #1 — V3 CREATE response 跟 V3 LIST response 欄位不一致 ⚠️

| Endpoint | `data.*` shape | 說明 |
|---|---|---|
| V3 CREATE response | `{ identifier, downloadPage, iPhoneUri, androidUri, barcodeValue, genericProperties: [], ErrorMessage: "" }` | 跟 `passcreator.ts::extractPassIssueData` 預期對得起來 ✅ |
| V3 LIST response（每個 item）| `{ identifier, linkToPassPage, barcodeValue, autoGeneratedId, ..., voided, notYetValid, createdOn, modifiedOn, expirationDate, ... 40+ 欄位 }` | **沒有** `downloadPage` / `iPhoneUri` / `androidUri`；用 `linkToPassPage` |

**對 SAOME backend 的影響**：今天的 `extractPassIssueData` 只吃 CREATE shape（SAOME flow 是 registerV3 create），所以**目前 production 不會撞到**。但任何未來想 hit V3 list endpoint（retention / dashboard / monitoring）的 consumer 會 silently 抓不到 download URL。

**修法（next session）**：parser 加 `linkToPassPage → downloadPage` fallback，或拆成 `extractPassIssueDataForCreate` + `extractPassIssueDataForList` 兩個 entry。

### Drift #2 — V3 error envelope 用 `errors: string[]`，不是 V2 的 `errors: {property, message}[]` ⚠️

真實 V3 capture：
```json
{
  "statusCode": 400,
  "success": false,
  "description": "Bad request",
  "errors": ["Template not found!"],       // ← string 陣列
  "count": 0,
  "responseMetaData": null,
  "data": { ... }
}
```

`passcreator.ts::normalizePasscreatorErrorEntries` 只處理：
- `errors: Array<{property, message}>` （V2 standard）
- `errors: {property, message}` （V2 singular object，verified 2026-10-11）

**V3 的 `errors: string[]` 完全沒處理** → `upstreamErrors` 回傳空陣列 → frontend banner 看不到 per-field reason，只看到 "Bad request"。

**對 SAOME backend 的影響**：V3 failure 時 user 看不到「哪個欄位」錯，只有 generic message。Production register flow 已知 Q2（barcodeValue literal）也是相同 root cause（parser 沒對 V3 真實 shape 做 defensive 處理）。

**修法（next session）**：`normalizePasscreatorErrorEntries` 加 string-array 分支，wrap 成 `{property: '<v3-context>', message: <string>}`。

### Drift #3 — Q2 真 root cause：`barcodeValue: "no value specified"` 是 literal string ⚠️⚠️⚠️

**真實 V3 create response 確認**：
```json
{
  "data": {
    "identifier": "c2da13bc-2bab-4da8-837d-2857c7e23aee",
    "downloadPage": "https://app.passcreator.com/en/p/...",
    "iPhoneUri": "https://app.passcreator.com/en/passinstance/pkpass?...",
    "androidUri": "https://passwallet.page.link/?apn=com.attidomobile.passwallet&link=...",
    "barcodeValue": "no value specified"     ← ⚠️ LITERAL 字串
  }
}
```

真實 V3 list response 也驗證同樣 pattern（每個沒 barcode 設定的 pass 都回 `"no value given"` 或 `"no value specified"`）。**至少 2 個 literal 變體**：
- `"no value given"` — 出現在 list 沒有 barcode 的項目（observation #1）
- `"no value specified"` — 出現在 create response（這次 capture）

`extractPassIssueData` 把它當合法 string 寫進 `pass_holders.barcode_value`。Production register 完後 DB 欄位就是 `"no value specified"`，不是 NULL，也不是真 barcode。

**修法（next session）**：parser 加 defensive normalize：
```typescript
const BARCODE_VALUE_PLACEHOLDERS = new Set(['no value given', 'no value specified', 'no barcode', '']);
const normalized = BARCODE_VALUE_PLACEHOLDERS.has(rawBarcodeValue) ? null : rawBarcodeValue;
```

### Drift #4 — `iPhoneUri` 不是 `.pkpass` 直連；`androidUri` 是 Passwallet 不是 Google Wallet ⚠️

User 上一輪 spec 假設：
- `iPhoneUri = "https://app.passcreator.com/linkToPassFile.pkpass"`
- `androidUri = "https://pay.google.com/save/linkToGoogleWalletPassUri"`

真實 V3 抓下：
- `iPhoneUri = "https://app.passcreator.com/en/passinstance/pkpass?passInstance%5B__identity%5D=<id>&t=<token>"`
- `androidUri = "https://passwallet.page.link/?apn=com.attidomobile.passwallet&link=https%3A%2F%2Fapp.passcreator.com%2Fen%2Fpassinstance%2Fpkpass%2F<id>"`

差異：
- `iPhoneUri` URL 多了 query params + `/en/passinstance/` path。功能同（都 serve .pkpass），但格式不同。
- `androidUri` 是 **Passwallet** deep link（`passwallet.page.link`），**不是** Google Wallet（`pay.google.com`）。User spec 寫錯。SAOME backend `PassHolderPassDownload::pickDownloadUri` 用 `iPhoneUri` / `androidUri` / `downloadPage` 三選一，**user-agent detection 還會跑**，所以不會壞；但 "Save to Google Wallet" 的文案可能誤導。

**對 SAOME backend 的影響**：
- `iPhoneUri` URL 變了 → Apple Wallet CTA 仍 OK（仍是 .pkpass endpoint）
- `androidUri` 是 Passwallet 而非 Google Wallet → 如果前端 copy 寫 "Save to Google Wallet" 是錯的，應該是 "Save to Passwallet" 或通用 "Add to Wallet"
- i18n key `passHolder.download.android` 的值需要 verify

**修法（next session）**：verify i18n copy（`passHolder.download.android*`）+ 確認 `pickDownloadUri` UA detection 是否仍正確（iOS → iPhoneUri ✅、Android → androidUri ✅、desktop → downloadPage ✅，三條都還能 work；只是 user 心智 model 對 Android 那條是 Passwallet 不是 Google Wallet 要重新 align）。

### Drift #5 — `genericProperties` 是 `[]` 不是 `{}`

User 上一輪 spec 假設 `data.genericProperties: { ... }`（object）。真實 capture 是 `data.genericProperties: []`（array）。`passcreator.ts` docblock 寫「`genericProperties: { ... }`」也是錯的，但 SAOME backend 沒讀這個欄位，所以**目前沒影響**。Note 給未來 reader。

## Capture Script 的 SOP（給 future invariant）

1. **API key 來源**：`.dev.vars` first → `process.env.PASSCREATOR_API_KEY` fallback。如果兩者都缺 → exit 2 + 明確訊息
2. **Template ID 來源**：`process.env.PASSCREATOR_V3_TEMPLATE_ID` 必須是 UUID。fallback 預設是 `KNOWN_TEMPLATES[0]`（probe 過的 production UUID）。如果 format 不是 UUID → exit 2 + 明確訊息
3. **3 個場景**：
   - `v3-list`：GET `/api/v3/pass` — 永遠 safe，不污染 production
   - `v3-create-error`：POST `/api/v3/pass?async=false` with `data.templateId` 故意 omitted → Passcreator 回 "Template not found!" — 抓 V3 error envelope shape
   - `v3-create-success`：POST `/api/v3/pass?async=false` with valid template + 4 holder fields（non-ASCII name 順便測 workerd JSON.stringify round-trip）— **會在 production 真的發一個 pass**。用 `capture-test-<ts>@capture.invalid` email + dummy phone 避免跟真實 user 衝突。V3 沒 documented DELETE，cleanup manual if needed
4. **`--read-only` flag**：跳過 `v3-create-success`（不發 test pass）。可單獨跑 list + error 兩條做 audit
5. **Fixture 寫到 `fixtures/passcreator/v3/<scenario>.json`**，format 跟 V2 capture 一致（`{ scenario, description, capturedAt, apiUrl, request, response }`）讓 consumer 用同一個 `tryLoadFixture` helper
6. **Conformance test consumer**：`apps/backend/src/shared/lib/passcreator.test.ts` 擴充 `importFixturesGlob` 同時撈 V2 + V3 fixtures。V3 fixtures 用 `v3/<scenario>` key namespace（避免跟 V2 `success-create` 撞 key）
