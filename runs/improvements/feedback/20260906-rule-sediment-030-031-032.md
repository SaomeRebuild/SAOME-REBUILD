## 背景

`DEV/09-2026/0905-step4-autosave-slow-network-baseline.md` 完整 trace 了 Step 4 autosave 在 slow-network 下寫 empty defaults 進 DB 的事故。本文件不重述 trace，只解釋為什麼 trace 結果必須以 **3 條不同 rule** 沉澱。

### 三角形破口

```
        Effect 第一次 run
        (useEffect 內讀 store 值)
                ↓
        [Rule 030 守門]
                ↓
        ≥1s timer (autosave debounce)
                ↓
        [Rule 031 守門]
                ↓
        async fetch race (getById 解析時間不定)
                ↓
        [Rule 030 + 031 必須同時守]
                ↓
        JSONB merge (silent overwrite)
                ↓
        [Rule 032 三層防護]
```

**3 個機制各處理一塊** — 缺一就壞：

| 機制 | 失敗 mode | 守門 rule |
|------|-----------|------------|
| Effect 第一次 run 不可信 | mount 時 `reset()` 跑完，store 是 empty defaults | Rule 030 |
| 長 timer + async fetch race | `getById > 1s debounce` → 帶 empty PUT 出去 | Rule 031 |
| 後端 `||` JSONB merge | empty values silent overwrite 不 throw | Rule 032 |

## Rule 030 — Effect 第一次 run 不可信 SOP

### 觸發條件

任何 React `useEffect`，且該 effect：
1. 依賴外部資源（Zustand / TanStack Query / context）的 store 值
2. 該 store 值由 `async fetch` 取得（`useEffect` → `setXxx()` → `fetch().then(setXxx)`）
3. effect 內有副作用（PUT / dispatch / setTimeout 等）

### 強制的 pattern

```typescript
const baselineArmedRef = useRef(false);
const lastSnapshotRef = useRef('');

// Reset on session boundary
useEffect(() => {
  baselineArmedRef.current = false;
  lastSnapshotRef.current = '';
}, [sessionKey]);

useEffect(() => {
  if (!sessionKey) return;
  const snapshot = JSON.stringify(currentStoreValue);

  if (!baselineArmedRef.current) {
    // 第一次 run：純粹 seed baseline，不排 timer
    baselineArmedRef.current = true;
    lastSnapshotRef.current = snapshot;
    return;
  }

  if (snapshot === lastSnapshotRef.current) return;
  lastSnapshotRef.current = snapshot;
  // ... 排 timer / dispatch / PUT ...
}, [sessionKey, currentStoreValue]);
```

### 為什麼不只加 `if (description === '') return` 就好

常見錯誤修法：「看 store 是 empty defaults 就 skip」：

```typescript
// ❌ 仍然壞
useEffect(() => {
  if (description === '' && backFields.length === 1 && backFields[0].value === '') return;
  scheduleTimer();
}, [cardId, description, backFields, links]);
```

問題：使用者第一個字時不再是 empty，但 `loadSettings` 還沒完成 → schedule 一個帶半空資料的 PUT；`getById` 慢於 debounce → 帶 stale 半空 PUT 出去。

**baselineArmedRef 守「第一次 run 純粹 seed baseline」** — 物理上保證就算 fetch 慢，第一次 run 也不會出去寫東西。

### Conformance test

```typescript
it('does NOT autosave empty defaults when getById resolves slowly (regression 2026-09-05)', async () => {
  vi.useFakeTimers({ shouldAdvanceTime: true });

  vi.mocked(cardService.getById).mockImplementationOnce(
    () => new Promise(resolve => setTimeout(() => resolve({
      id: 'test-template-id',
      settings: FULL_SETTINGS,
    }), 1500)),
  );

  renderWithRouter();

  await act(async () => { vi.advanceTimersByTime(1100); });

  const emptyPayloads = updateCalls.filter(u => {
    const s = (u.payload as { settings?: Record<string, unknown> })?.settings ?? {};
    return s.description === '' && /* ... empty defaults pattern ... */;
  });
  expect(emptyPayloads).toHaveLength(0);
});
```

沒有這條 regression test → 不可 ship。

## Rule 031 — 長 timer + async fetch 是雷區

### 觸發條件（ms 分級）

| ms | 風險 | 處理 |
|----|------|------|
| < 100 | 低 — fetch 幾乎一定先 resolve | 直接寫 |
| 100-500 | 中 — production edge cache miss 可能比這慢 | 仍建議 baseline-armed |
| 500-1000 | 高 — cloudflare cold start 偶爾會撞 | baseline-armed **必須** |
| **≥ 1000** | **雷區** | baseline-armed + slow-network regression test **MANDATORY** |

### 為什麼 1s「看起來很短」其實不夠

| 情境 | getById resolve 時間 |
|------|---------------------|
| 本地開發（localhost）| < 50ms |
| Cloudflare edge cache hit | < 200ms |
| Cloudflare edge cache miss + warm Hyperdrive | 300-700ms |
| Cloudflare edge cache miss + cold Hyperdrive（worker idle > 60s）| 1000-3000ms |
| Mobile 4G + cold Worker | 1500-5000ms |
| Mobile 3G + cross-region | 3000-10000ms |

只要「debounce ≥ fetch resolve 時間」這個不等式成立，bug 就會重現。

### timer fire 時讀 store.getState()，不 capture 閉包

```typescript
// ❌ 閉包陷阱
useEffect(() => {
  timerRef.current = setTimeout(() => {
    cardService.update(cardId, { settings: { description, ... } });
    //                                       ^^^^^^^^^^^^^^^^^^
    //                                       effect 跑時的閉包變數
  }, 1000);
}, [cardId, description, ...]);

// ✅ 讀 store.getState() 拿最新值
useEffect(() => {
  timerRef.current = setTimeout(() => {
    const s = useStore.getState();
    cardService.update(cardId, { settings: { description: s.description, ... } });
  }, 1000);
}, [cardId]);   // deps 只放 sessionKey
```

### Cleanup 必清 timer

```typescript
useEffect(() => {
  if (timerRef.current) clearTimeout(timerRef.current);
  timerRef.current = setTimeout(() => { /* ... */ }, 1000);

  return () => {
    if (timerRef.current) {
      clearTimeout(timerRef.current);
      timerRef.current = null;
    }
  };
}, [...]);
```

`setInterval` 不會被 effect re-run cancel — 必須在 cleanup 顯式清。

## Rule 032 — 後端 JSONB merge 是 silent killer

### 觸發條件

任何後端 UPDATE / INSERT 涉及 jsonb column（`settings`、`metadata`、`config` 等），且 merge 邏輯用 PostgreSQL `||` operator 或 `jsonb_set()`。

### 鐵律 1：後端必須 validate incoming jsonb（schema-level rejection）

```typescript
// ✅ 正確：zod 拒絕 description='' 就 400 回去
const TemplateSettingsSchema = z.object({
  description: z.string().min(1, 'validation.descriptionEmpty'),
  backFields: z.array(/* ... */).min(1, 'validation.backFieldsEmpty'),
  links: z.array(/* ... */).default([]),
});

await sql`
  UPDATE templates
     SET settings = settings || ${sql.json(TemplateSettingsSchema.parse(input.settings))}
   WHERE id = ${id}
`;

// ❌ 危險：直接透傳
await sql`
  UPDATE templates
     SET settings = settings || ${sql.json(input.settings as any)}
   WHERE id = ${id}
`;
```

### 鐵律 2：前端必須在 PUT 之前做 client-side validation

```typescript
// 前端：autosave timer fire 之前
const parsed = TemplateSettingsSchema.safeParse({ description, backFields, links });
if (!parsed.success) {
  console.warn('[CardBuilderEditor] autosave blocked — invalid state:', parsed.error.issues);
  return;   // 不 schedule PUT
}

scheduleTimer(() => cardService.update(cardId, { settings: parsed.data }));
```

### 鐵律 3：使用 `sql.json()` 注入（workerd pitfall）

```typescript
// ✅ 正確
sql`settings = settings || ${sql.json(input.settings)}`

// ❌ 危險（workerd 破壞 non-ASCII）
sql`settings = settings || ${JSON.stringify(input.settings)}::jsonb`
```

詳見 `runs/.../20260831-workerd-json-stringify-jsonb-pitfall.md`。

### 鐵律 4：DB CHECK constraint 是最後防線

```sql
ALTER TABLE templates
  ADD CONSTRAINT settings_not_empty
  CHECK (
    settings ? 'description'
    AND (
      settings->>'description' != ''
      OR jsonb_array_length(settings->'backFields') > 0
      OR jsonb_array_length(settings->'links') > 0
    )
  );
```

但 trigger / CHECK 是「如果有人 bypass 也要 fail」，**不是** 主守門員。前端 + 後端 application 層 validation 必須先擋。

## 為什麼是 3 條獨立 rule 而不是 1 條

| 候選方案 | 評估 |
|---------|------|
| 1 條綜合 rule | ❌ 太長、關注點混雜、無法對應「具體什麼時候觸發」 |
| 3 條獨立 rule（採用）| ✅ 各自對應獨立 root cause，互不干擾，trigger 條件精確 |
| 4+ 條更細 rule | ❌ 過度拆解，Conformance test 模板難統一 |

3 條 rule 互補、但又各自獨立 — 任何 code review / agent 觸發時可以精確定位該引哪一條。

## 教訓

1. **「Effect 第一次 run + 長 timer + async fetch」三角形是標準 SOP 破口** — 三者各處理一塊，缺一就壞
2. **baselineArmedRef pattern 是 universal 的**：Step 4 / name autosave / 未來任何 autosave 場景都適用
3. **`store.getState()` + cleanup 顯式清 timer 是基本盤**：不能用閉包捕獲，但也不能省略 cleanup
4. **JSONB `\|\|` operator 是 silent overwriter**：empty value silent overwrite 不 throw，三層防護（前端 zod + 後端 zod + DB CHECK）是 MANDATORY
5. **慢網路 regression test 是這類 effect 的標配**：1000ms 是 critical threshold，不是 1s 都會撞
