## 根因分析

### 缺乏閉環 discipline

| 缺 | 後果 |
|----|------|
| ❌ 沒有 CI gate 驗證「`.sql` 檔案存在 ≠ production 套用」| migration 漏 apply 沒人抓到 |
| ❌ 沒有 registry 追蹤「哪些 migration 已套過」| 多 agent 並行時一個補 apply 另一個不知 |
| ❌ MCP timeout 處理無 SOP | agent 跳過 apply 提交 workaround |
| ❌ Naming convention 無強制 | 同日多個 migration 排序不明 |

## 修法 — 3 components + Rule 035

### 1. CI gate — `apps/backend/scripts/check-migrations-applied.cjs`

```js
// Walk supabase/migrations/*.sql, verify every filename has matching entry
//   in .applied-migrations.json. Detect missing entries, orphan entries,
//   duplicate basenames (case-insensitive FS), and non-conforming filenames.
// exit 0/1/2 with actionable error messages.
```

行為表：

| 情境 | exit code | 訊息 |
|------|-----------|------|
| 每個 `.sql` 都有 registry entry | 0 | `OK: 14 migrations registered as applied.` |
| 有 `.sql` 但 registry 缺 | 1 | `FAIL: 1 migration file(s) have NO registry entry` |
| registry 引用了不存在的 `.sql` | 1 | `FAIL: 1 registry entry(ies) reference a missing file` |
| registry 檔案不存在或壞 JSON | 2 | `FAIL: registry file missing / not valid JSON` |
| `.sql` 沒 `^\d{8}` prefix | 1 | `FAIL: migrations with non-conforming filenames` |
| 同名 file（case-insensitive）| 1 | `FAIL: duplicate migration filenames detected` |

### 2. Registry — `supabase/migrations/.applied-migrations.json`

Source-of-truth contract。每個 `.sql` file 必須有對應 entry：

```jsonc
{
  "_comment": "...",
  "_format_version": 1,
  "applied": [
    {
      "filename": "20260905000001_015_init_revoked_tokens.sql",
      "applied_at": "2026-09-05",
      "applied_by": "auth-logout-phase-2.2",
      "via": "saome_supabase-mcp",
      "notes": "optional — what problem this solved"
    }
  ]
}
```

| 必填欄位 | type | 說明 |
|---------|------|------|
| `filename` | string | 必須跟 `.sql` 檔名完全對應 |
| `applied_at` | string YYYY-MM-DD | 套 migration 的日期（不是 commit 日期）|
| `applied_by` | string | 工作 stream / feature 名稱 |
| `via` | string | `saome_supabase-mcp` / `manual-supabase-dashboard` / `manual-psql` |
| `notes` | string? | optional — 這條 migration 解了什麼問題 |

### 3. Workflow job — `.github/workflows/deploy.yml`

新增 `migrations` job：

```yaml
migrations:
  runs-on: ubuntu-latest
  if: |
    always()
    && github.event_name == 'push'
    && contains(needs.path-filter.outputs.changes, 'migrations')
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with:
        node-version: '20'
        cache: 'npm'
        cache-dependency-path: 'package-lock.json'
    - run: npm ci
    - run: npm run check:migrations --workspace=apps/backend
```

`path-filter` 改為在 top 輸出 `migrations` (改 `dorny/paths-filter@v3` 設定)。

## Rule 035 — Migration Apply Pipeline 8-Section Discipline

### § 1 — 三步驟完成

```
1. 寫好 SQL 檔 (follow naming convention)
2. 立刻呼叫 saome_supabase::apply_migration
3. 回 success 後,立刻 append registry entry
```

### § 2 — Registry 是 contract

每個 `.sql` 必填 entry（見上方 schema）。

### § 3 — CI gate MANDATORY

`npm run check:migrations --workspace=apps/backend` 必在 `prebuild` hook 跑。每次 backend build 必觸發。

### § 4 — MCP timeout / 失敗處理

| 情境 | 行動 |
|------|------|
| `apply_migration` 成功 | 立刻 append registry entry；commit SQL + registry update 同 PR |
| `apply_migration` timeout | **不要** commit SQL 檔 — 等 MCP reconnected 再 apply |
| `apply_migration` 回 "column already exists" | 表示已被別的 stream apply — append registry entry,`notes` 標 `reapplied-already-exists` |
| `apply_migration` DB error | 修 SQL 再 retry；不要改 committed 但未 apply 的 SQL |

### § 5 — 撤回 migration protocol

| 動作 | 必做 |
|------|------|
| 刪除 `.sql` 檔 | 同 PR 從 `.applied-migrations.json` 移除 entry |
| 修改 committed 但未 apply 的 `.sql` | 直接覆寫原檔 |
| 修補已 apply 的 `.sql`（bug fix）| 新建 `YYYYMMDD_HHMMSS_<seq>_<fix-name>.sql` |

### § 6 — Naming convention（MANDATORY）

```
YYYYMMDD[_HHMMSS]_NNN_<name>.sql
```

| Pattern | 範例 |
|---------|------|
| Bootstrap | `20260727_init_saome_schema.sql` |
| 編號遷移 | `20260821000001_006_add_templates_expires_at.sql` |
| 含 timestamp 解碰撞 | `20260831000004_013_trigger_reject_non_object_settings.sql` |

不準：

| ❌ | 原因 |
|----|------|
| `add_email.sql` | 沒日期前綴、無法 reorder |
| `2026-09-05_init_x.sql` | 用 dash 而非 YYYYMMDD number |
| `m_001_x.sql` / `001_x.sql` | 沒日期前綴或順序不可考 |

### § 7 — 跟 Decision Log / Rule 019 的關係

| 規則 | 角色 |
|------|------|
| `019-schema-contract-drift.mdc` | DB ↔ schema ↔ backend request 四層同步（schema 層）|
| `035-migration-apply-pipeline.mdc`（本檔）| DB schema 變更 **必須 apply 才不會 production 500**（deploy 層）|
| `001-methodology.mdc` § Decision Log | 「新增 DB column migration」「新增 DB table」是 P0 架構改動，必進 `runs/decisions/` |

### § 8 — 同 PR 帶齊四件事

新增 `supabase/migrations/<file>.sql` 的 PR，**必帶**：

```
[apps/.../db/<table>.ts]                  # INSERT/UPDATE 參數列
[apps/.../schemas/request.ts]             # backend request schema (Rule 019 §4.1 第四層)
[apps/.../services/...]                   # service signature 參數
[.applied-migrations.json]                # 套完 MCP 後 append entry
[vitest conformance test]                 # 新欄位讀得到
```

任一缺 → follow-up drift 風險。

## 教訓

1. **「`committed == applied` 是 silent assumption」** — 但實際上 100% 會產生事故，必須有 CI gate 才能安心
2. **3 components 必須組合**：只有 registry 不夠、只有 CI gate 不夠、只有 rule 不夠 — 三者一起才有 closure
3. **Backfill 是 cold start 的代價**：14 條 entries 必須填齊，否則 CI fail
4. **MCP timeout 是必然事件**：必須有明確 protocol「不要 commit workaround，等 MCP reconnected 再 apply」
