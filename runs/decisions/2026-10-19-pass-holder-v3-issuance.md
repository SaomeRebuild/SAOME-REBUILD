# Decision：Pass Holder V3 簽發（Passcreator `/api/v3/pass`）落地

**日期**：2026-10-19
**作者**：SAOME-REBUILD
**Scope**：L3 Heavy（DB migration + 第三方 API 包裝 + backend service 接線 + frontend 改寫）

---

## 背景

`/pass/{templateId}` 公開頁讓 visitor（Pass Holder）填寫 4 個 pass-delivery 欄位（name / phone / birthday / email）並送出註冊。Backend 目前完成 `upsertPassHolder` 並回 `passHolderId`，前端 `PassHolderRegistrationSuccess` 顯示「Pass 下載功能即將上線」的 placeholder。Holder 還沒拿到實體 wallet pass。

2026-10-16 single-CTA feedback 把 Pass creator V3 整合列為 **follow-up #3**：「當付費完成後呼叫 Passcreator `/v3/pass` 推送實體 pass」。Follow-up #3 一直未落地，本 session 把它從 P1 follow-up 推到 P0 並 shipping。

### 設計觀察

從 `https://developer.passcreator.com/en/api/v3/pass` 的 list response 可看到 per-pass runtime 物件：

```json
{
  "identifier": "a0f629e6-6533-40cb-90b8-ef9093bfbb26",
  "autoGeneratedId": "r38extwgahfu30z3og667ea1a6ed76c",
  "templateId": "1233456-12345-45646",
  "linkToPassPage": "https://app.passcreator.com/en/p/123456789123456789",
  "barcodeValue": null,
  "firstDownloadedAt": null,
  ...
}
```

5 個欄位是 per-pass 發行後需要的：
- `identifier`（pass UUID）— 寫進 `pass_holders.pass_identifier`（防重複發行、reference 用）
- `linkToPassPage` — 寫進 `pass_holders.download_url`（前端給使用者點的 .pkpass 連結）
- `barcodeValue` — 寫進 `pass_holders.barcode_value`（前端顯示條碼）
- `firstDownloadedAt` / `expirationDate` — 本 PR 不存，後續 retention / expiry 流程需要時再開 Decision Log

### V3 payload 形狀

User 在 plan mode 確認：「**V3 不區分 primary/secondary，全部 4 個持有人欄位走 additionalProperties**」。理由是 V3 是 per-pass runtime 端點，不像 V2 template 端點有 `{memberName}` / `{phone}` 這種 placeholder 區分 — V3 端把整包 key-value 推進去，Passcreator 端按 template V2 設計的 placeholder 自動 routing。

→ 程式端不需要在 backend 重新 map 哪個 field 進 primary / secondary / additional，全部走同一個 `additionalPropertyValues`。

## 選項與決定

### Schema：A — 在 `pass_holders` 加 5 個 column（決定 ✅）

| 欄位 | 型別 | Nullable | 用途 |
|---|---|---|---|
| `pass_identifier` | TEXT | yes | V3 回的 `data.identifier`；防重複發行 / reference 用 |
| `download_url` | TEXT | yes | V3 回的 `data.linkToPassPage`；前端 CTA 連結 |
| `barcode_value` | TEXT | yes | V3 回的 `data.barcodeValue`；前端 barcode display |
| `issued_at` | TIMESTAMPTZ | yes | 簽發時間；NULL = 失敗或尚未發行 |
| `issuance_error` | TEXT | yes | 失敗時的 i18n key（如 `'common.error.upstreamFailed'`） |

**理由**（沿用 023 / 024 模式）：

1. 一 row 一 transaction，整個 register flow 維持 atomic，沒有跨表 join
2. CHECK constraint 不需太多 — 5 個欄位都是 TEXT/TIMESTAMPTZ；非 enum 不需 CHECK
3. 既有 row 不破壞（全部 nullable，無 default；user 在 q3 已表態 ignore 測試資料）
4. 與既有的 `selected_tier_index` / `membership_tier_snapshot` / `payment_provider` / `payment_status` / `paid_amount` / `currency` 6 個欄位並列，結構對稱
5. 真正金流上線後，`issuance_error` 可加進 Sentry / log 監控失敗率

### V3 呼叫時機：B — 註冊成功立即發行（決定 ✅）

| 候選 | 行為 |
|---|---|
| 候選 A：on-demand lazy | 使用者點「下載」按鈕才發；user flow 多一步；好處是不用處理 race |
| 候選 B：註冊成功立即發（決定） | `registerService` 內 `upsertPassHolder` 完成後立即 sync 呼叫 `issuePass()`；好處是 user 完成註冊後「下一個 view 就是下載」，單一 click flow |
| 候選 C：Cron 批次發 | 排程跑；user 完全沒體驗；對 mock flow 是 over-engineer |

理由：候選 B 對 mock-stage / paid-stage 統一（user 在 q4 已同意）、UX 最佳 — 註冊成功就看到下載按鈕，不需要第二步操作。

**失敗處理**（q8-a 已確認）：

- `issuePass` 失敗不 throw — `registerService` 用 try/catch 包起來
- 寫 `issuance_error` i18n key（例如 `'passHolder.errors.upstreamFailed'`）進 DB row 而不是 throw
- 註冊 HTTP response 仍回 **200** — 因為 row 已經寫好了（pass_holder 的內容是有意義的）；前端看到 `issuance: { issuanceError: '...' }` 就顯示「重試簽發」按鈕
- `BadGatewayError` 仍然進 SaomeError 邊界（`shared/middleware/errorHandler.ts` 已 wired），但只會在 caller 用 `issuePass` 自己做 health-check 時才 throw（例如 dashboard 的 "test passcreator connection" 工具 — out of scope for this PR）

### 第三方包裝位置：C — 沿用 `shared/lib/passcreator.ts`（決定 ✅）

| 候選 | 行為 |
|---|---|
| 候選 A：抽到 `shared/services/external/passcreator.ts` 對齊 Rule 000 Part C | 重構既有 `passcreator.ts`；本 PR 變大；scope creep |
| 候選 B：開新檔案 `shared/lib/passcreator-v3.ts` | 平行檔案；很快 drift |
| 候選 C：沿用 `shared/lib/passcreator.ts`，新增 `issuePass()` 函式（決定） | 與既有 `createPassTemplate` / `updatePassTemplate` / `fetchPassTemplate` 同檔；繼續一致的 V2/V3 風格 |

理由：該檔已是 SAOME 內 Passcreator upstream contract 的 owner（rule 036 § 7 提到的「未來若新增第二個第三方 provider 一起重構」不在本 PR scope）。後續若第二個第三方出現再抽，與 Rule 036 § 7 一致。

### Issue pass relation（2026-10-19 衍生）: 既有 row + 不重複發行

- `findPassHolderByTemplateAndEmail(sql, templateId, email)` 找到既有 row 時（如「同 email 再 register 一次」）：**不重新發行新 pass**（會造成一個 template 同一個 email 兩個 pass），直接以既有 `pass_identifier` / `download_url` 為準
- 既有 row 沒有 `pass_identifier` 才走 `issuePass`
- 新 row（首次 register）永遠走 `issuePass`

理由：與既有 idempotent register 對齊（Same email = 同一個 holder）。

## 2026-10-19 衍生：對齊 V3 docs 真實合約（root-cause fix for "全綠但拿不到 pass"）

### 觸發

User 反映：「全綠還是拿不到 pass 阿，你剛才有參照 https://developer.passcreator.com/en/api/v3/pass 去做嗎」。

抓 V3 docs 真實的「Create a Pass」section 後發現：上輪的 V3 contract 是**從 V3 list response + V2 update envelope 反推的**，**沒碰過真實 create endpoint**。4 個地方對不上：

| 上輪（錯）| V3 docs 真實（對）|
|---|---|
| URL `POST /api/v3/pass` | URL `POST /api/v3/pass?async=false`（docs 原文：「If you need to see the actual `barcodeValue` in the JSON response body, you need to set `async` to `false`」）|
| Body `{ templateId, additionalPropertyValues: { ... } }` | Body `{ data: { templateId, name, phone, birthday, email } }`（額外屬性直接放 data object 內，`additionalPropertyValues` 這個欄位 V3 create 不存在）|
| Wrapper return `downloadUrl` 從 `data.linkToPassPage` | Wrapper return `downloadPage` 從 `data.downloadPage`；V3 還多回 `iPhoneUri` + `androidUri`（拆 universal link 為 3 URI）|
| Response field `data.linkToPassPage` | Response field `data.downloadPage`（V1 field name；V3 改過了）|
