## 為什麼選「精簡 bridge」而非「新增 rule」

兩個 user-driven constraint：

1. **「怎樣的修改可以讓工作流更順暢，且消耗更少的資源？」** — 2026-08-08 AskQuestion 答案
2. **「在現有 3 個規則加 bridge 說明 + 交叉引用」** — layer-bridge 模式

計算依據（plan 估的 token 影響，verify 前先列出）：

| 選項 | 預估檔案變更 | 預估增量行數 |
|---|---|---|
| 開 5 個新 rule（020-*）| 5 新檔 | ~300+ 行 |
| 精簡 bridge + 1 script（本 plan）| 6 改 1 新 | ~225 行 |
| 整個 workflow 重組 | 10+ 改 | ~500+ 行 |

選 bridge 的理由：

- **既有 rule 已 cover Pattern 1 / 2 / 3 / 5 70-80%**，缺的只是 cross-reference 讓 agent 知道「這些 rule 是有關的」
- **新 rule 會增加讀檔成本**（每個新 session 都會讀所有 `.cursor/rules/*`），bridge 在既有 rule 內加 cross-link 反而是 zero-cost
- **Bug-7b 的 schema drift 是真正的 L3 Heavy work**（跨 5 個 module 建同形 conformance test），不是 L1/L2 trivial — 強塞進本次會破壞「少資源」原則
- **`session-recovery.e2e.test.ts` 要 brainstorm + happy-dom + cookie jar 整合**，先記 backlog 等獨立 session 做
