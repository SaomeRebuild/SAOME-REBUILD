## 我自己的反省（這次什麼沒做對）

1. **沒在 schema 對齊 commit 前先確認 shared 已經加 `businessEmail`**：
   Round 2 的「對齊」只對齊了 `min(1)` vs `min(2)` 的 field-by-field 比對，沒注意到 shared schema 有後端沒有的欄位（`businessEmail`）。`check-shared-schema-sync.cjs` 一跑才發現。
   預防：以後改 schema 對齊一定要先跑這個 script 把所有 drift 列出來。

2. **沒把 `tests/probe/register-probe.ts` 真的轉成 Playwright test**：
   Probe 證明了 autofill bug 的存在，但留在 `tests/probe/` 沒接到正式 test suite。如果下次 autofill 又 regression，這個 probe 還要手動跑才會抓。
   預防：probe 寫完當天就要轉成正式 test（不是留下當參考）。

3. **Schema sync script 的 regex parser 沒測過 `accountInfoBase.omit(...)` 的 case**：
   第一次寫只處理 `z.object({...})`，shared 用 `.merge()` + `.omit()` 就直接 false-positive 報一堆「只有 shared 有的欄位」。雖然後來加 `.merge()` 處理好了，但這暴露出 regex-based schema parser 本身就是 fragile 的。
   預防：未來如果 schema 組合方式變複雜（例如 `.pipe()`、`.transform()`），要直接用 `tsx loader` + `z.toJSONSchema()` 拿真正的 JSON Schema 來比對。

4. **沒把這次事故對應的程式碼修法（autofill dual-fix、schema 對齊）標 commit**：
   程式碼修法（`RegisterForm.tsx` 的 useEffect、`apps/backend/src/modules/auth/schemas/request.ts` 對齊）散在多個尚未 commit 的 modified files 裡。如果未來有人要 trace「這條 rule 對應的真實修法」，要從 plan 文件反向找回 commit，不直觀。
   預防：下次做事故 recovery，最後 commit 時 footer 要寫清楚「對應 rule 018 / 019」。
